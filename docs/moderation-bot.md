# Отдельный бот модерации

Отдельный токен и процесс, общий код Django и БД. Основной пользовательский бот не меняется. Из HTTP-запроса жалобы внешние вызовы не делаются: отдельный процесс читает сохранённые жалобы и доставляет их администраторам.

## Настройка и запуск

Создайте нового бота через `/newbot` в BotFather. В локальном `.env`, а при публикации отдельно в серверном `.env`, задайте:

```dotenv
MODERATION_BOT_TOKEN=токен_НОВОГО_бота
MODERATION_ADMIN_IDS=123456789,987654321
```

Нужны числовые Telegram ID людей, не username и не внутренние ID приложения. Добавьте хотя бы один заранее известный ID. Пустой или ошибочный список запрещает запуск. После запуска постороннему бот ответит отказом и покажет только его собственный ID — это помогает добавить остальных модераторов. Каждый администратор должен открыть нового бота и нажать `/start`, иначе Telegram не разрешит боту писать ему первым.

После изменения allowlist перезапустите процесс. Не публикуйте токен в Git или переписке. Токен основного бота не заменять и не использовать для модерации.

На Windows, в папке проекта после запуска PostgreSQL:

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py run_moderation_bot
```

Не запускайте локально polling с токеном уже работающего серверного бота. Для разработки используйте тестовый бот и локальную БД. `--once` делает один проход очереди и один короткий опрос Telegram; это не dry-run. Webhook автоматически не удаляется: при его наличии команда останавливается. PostgreSQL advisory lock запрещает второй экземпляр с тем же токеном на той же БД; между разными БД такой защиты нет.

## Команды и доступ

### Рабочая панель

Меню, очередь, история, карточка рынка, подтверждение и результат показываются в одном редактируемом сообщении. Очередь — список из пяти кнопок рынков, а не пять отдельных карточек. Постоянные кнопки «Жалобы», «История», «Главное меню» позволяют перемещаться без команд. Панель сохраняется в БД и используется после перезапуска.

Уведомления отделены от панели: одна компактная обновляемая сводка вместо потока полных карточек. При поступлении следующих жалоб сводка редактируется; редактирование не создаёт нового звукового push-уведомления. Кнопка «Открыть очередь» превращает сводку в рабочую панель, а прежнюю панель бот пробует удалить. Удаляются только известные боту собственные сообщения, не вся история чата. Если панель удалена пользователем, бот создаёт новую; при обычной сетевой ошибке не присылает дубликат.

Сообщения, накопившиеся до обновления интерфейса, не удаляются массово. Их можно один раз очистить вручную в Telegram. Для обновления интерфейса примените миграцию `0024_moderation_panels` и перезапустите процесс бота, затем отправьте `/start`.

После очистки истории отправьте `/start` (также подходят `/queue`, `/history`, `/id`). Явная команда создаёт свежую видимую панель и пытается убрать старую; кнопки продолжают редактировать панель на месте. Это необходимо, поскольку Telegram не сообщает боту о локальной очистке истории и может успешно редактировать уже невидимое пользователю сообщение. Ошибка удаления старой панели не блокирует ответ.

- `/queue` — новые жалобы, по пять рынков на страницу.
- `/history` — рассмотренные рынки, причины и последнее решение; полная история — в админке.
- `/id` — собственный Telegram ID.

Команды и callback-кнопки доступны только в личном чате разрешённого администратора. Каждое действие проверяет права на сервере. Групповой чат не получает очередь даже от администратора. Allowlist даёт глобальный доступ к жалобам, включая приватные рынки: добавляйте только доверенных людей.

Каждая жалоба, включая первую и созданные до запуска бота, доставляется каждому разрешённому ID. При недоступности Telegram или пока модератор не начал диалог доставка повторяется с задержкой; очередь доступна независимо от доставки.

## Решения

Карточка содержит вопрос, критерий результата, статус, число жалоб, причины и ссылку на Django-админку. Каждое решение требует отдельного подтверждения:

1. **🚫 Скрыть рынок — есть нарушение.** Все новые жалобы данного рынка получают статус «Подтверждена», рынок скрывается. Подтверждающая кнопка — «Да, скрыть рынок». Существующие правила сервиса запрещают торговлю скрытым рынком.
2. **✅ Оставить рынок — нарушения нет.** Все новые жалобы рынка получают статус «Отклонена». Автоматическое скрытие снимается. Если рынок ранее был отдельно скрыт модератором, кнопка называется «✅ Новые жалобы без оснований», а подтверждение явно предупреждает, что рынок останется скрытым.
3. **Вернуть в ленту** — отдельная кнопка в истории для скрытого рынка без новых жалоб. Она снимает прежнее скрытие; устаревшая кнопка не отменяет более новое решение. Завершённый рынок или истёкший дедлайн не открываются заново.
4. **⛔ Отменить рынок и вернуть монеты** — отдельное денежное действие с явным подтверждением. Работает для незавершённых торговых рынков: как по новым жалобам, так и после прежнего скрытия в истории.

Решение применяется ко всем ожидающим жалобам только выбранного рынка. Повтор и старая карточка не меняют уже принятое решение. Новые отклонённые жалобы не отменяют прежнее подтверждённое скрытие. История и причины не удаляются; рассмотренные жалобы не входят повторно в порог автоматического скрытия. Ограничение «одна жалоба на рынок от участника» сохранено.

**Скрытие и отмена различаются.** Скрытие не меняет балансы и не останавливает существующий фоновый механизм определения исхода и выплат. Отмена окончательно переводит рынок в «Отменён», прекращает процесс назначения исхода и выполняет возвраты через денежный сервис. Отменённый рынок нельзя восстановить кнопкой из старого сообщения. Уже разрешённые рынки с выполненными выплатами этим действием не пересчитываются. Проверку текста до публикации эта функция не добавляет.

### Правило полного возврата при модераторской отмене

- Возвращается `max(сумма покупок с комиссиями − уже полученные суммы продаж, 0)` по истории сделок каждого участника. Пример: купил на 100, получил 40 от продажи — возврат 60. Ничего не продавал — возврат 100. Продал за 120 при покупках на 100 — нового возврата нет, полученная прибыль не отбирается.
- Положенные возвраты не уменьшаются пропорционально: нехватку резерва компенсирует платформа виртуальными монетами. Сумма компенсации записывается в `Question.refund_compensation` и доступна в админке. В журнале балансов весь возврат отражается как REFUND.
- Автор теряет внесённую стоимость создания рынка и не получает комиссию создателя. Второй раз стоимость создания с него не списывается.
- Нерассмотренные залоги за споры по отменённому рынку возвращаются отдельно и однократно. Обычные отмены по другим причинам сохраняют прежние правила.
- Решение по жалобам, балансам, возвратам и исходу атомарно; повтор и параллельные нажатия не начисляют деньги дважды. Пользовательские уведомления об отмене отправляет штатный воркер из окончательного состояния.
- Ранее скрытые рынки автоматически не отменяются. Нужно отдельно выбрать отмену в карточке и подтвердить последствия. Споры о ДА/НЕТ по-прежнему решаются в существующей Django-админке.

Для обновления нужна миграция `0025_moderation_cancellation` и перезапуск бота. Миграция добавляет учёт компенсации и тип решения, но сама не меняет балансы и не отменяет существующие рынки.

## Хранение и надёжность

- `MarketComplaint` хранит статус, время и исполнителя решения.
- `ModerationAction` — неизменяемая через админку история: действие, `telegram:<id>` или `django:<user_id>`, время и число жалоб.
- `Question.moderation_hidden` отличает модераторское скрытие от автоматического.
- `ModerationDelivery` — отдельная доставка жалобы каждому администратору, с арендой строки на две минуты, повторами и временем успеха.
- `ModerationBotState` — offset Telegram polling по хешу токена. Сам токен в БД не хранится.
- `ModerationPanel` — ID рабочей панели и сводки уведомлений отдельно для каждого администратора и токена бота.

Сетевой обрыв после фактической отправки, но до сохранения подтверждения может привести к повторному уведомлению. Абсолютное exactly-once внешней доставки не обещается; решения в БД защищены от повторов. Апдейты подтверждаются после обработки, решения по рынку сериализуются блокировкой PostgreSQL.

В Django-админке доступны жалобы с фильтром статуса и действиями «Подтвердить» / «Отклонить», история решений и состояние доставок. Старое действие возврата в ленту теперь сохраняет жалобы вместо удаления. Нужны права staff и `market.change_question`, а также доступ к соответствующему разделу.

## Сервер

Добавлен `deploy/systemd/pm-moderation-bot.service`. `deploy/update.sh` устанавливает unit и включает/перезапускает его, только если обе переменные MODERATION_* заданы. Без настроек сервис выключен; удаление конфигурации с последующим обновлением останавливает его. При ошибке systemd перезапускает процесс.

Перед первым обновлением сделайте резервную копию БД. Миграция `0023_moderation_bot` добавляет поля и таблицы, не меняя балансы. Используйте фактическую серверную ветку: merge в другую ветку не означает публикацию. После публикации кода и заполнения серверного `.env` ответственный запускает обычный `deploy/update.sh`; он применит миграцию и подключит сервис.

```bash
systemctl status pm-moderation-bot
journalctl -u pm-moderation-bot -n 50 --no-pager
```

Сам по себе этот код не подключается к серверу и не создаёт бота в BotFather.

## Проверка

### Кто писал боту

Кнопка «👤 Кто писал боту» и команда `/contacts` доступны только администраторам.
Показывают имя, username, числовой Telegram ID, доступ, время первого и последнего обращения.
Записываются личные сообщения и нажатия кнопок, включая пользователей без доступа.
Один пользователь занимает одну запись; повторные обращения обновляют имя и время.
Тексты сообщений не сохраняются. Обращения до установки этой версии восстановить нельзя:
попросите человека снова отправить `/start`. Этот журнал не выдаёт права автоматически.
Для выдачи доступа добавьте ID в `MODERATION_ADMIN_IDS` серверного `.env` и перезапустите сервис.
Журнал также доступен в Django-админке только для чтения с поиском по ID, имени и username.

Обновление: после доставки кода на сервер выполните `manage.py migrate` от `pm`
(или штатный `deploy/update.sh`), затем `systemctl restart pm-moderation-bot`.
Миграция `0029_moderationcontact` добавляет таблицу и не меняет балансы.

### Споры об исходе

В главном меню добавлены «Споры об исходе» и отдельная «История споров».
Команды: `/disputes`, `/dispute_history`. Жалобы на нарушения остаются в своём разделе.
Новый спор доставляется каждому настроенному администратору с повторами при ошибках Telegram.
Карточка содержит критерий, исход и комментарий автора, аргументы участников (по три на страницу), залоги.
Для файла на сайте и Telegram-фото есть кнопка получения копии от бота модерации.
Последняя скачивает файл через API основного бота, затем загружает его отдельным ботом; основной polling для этого запускать не нужно.
Фото приходит отдельным сообщением, навигация по-прежнему работает в одной панели.

Решения: подтвердить исход автора, выбрать другой исход или аннулировать. Каждое требует подтверждения.
Используется существующий `services.moderator_decide`: изменился исход — залоги возвращаются и автор теряет стоимость создания;
исход остался — залоги не возвращаются. Отмена по спору полностью возвращает положительные чистые вложения
(покупки с комиссиями минус выручка от продаж). Недостаток резерва компенсирует платформа,
сумма записывается в `refund_compensation`. При отмене все открытые залоги возвращаются,
автор теряет стоимость создания, уже полученная прибыль участников сохраняется.
Выплаты выполняются при подтверждении, а уведомления участникам отправляет обычный worker.
Если до подтверждения поступил новый спор, карточку нужно открыть заново. Два администратора не могут провести расчёт дважды.
Решение бота сохраняет Telegram ID модератора и время в `DisputeDecision`, доступном только для чтения в Django-админке.

Локальный запуск из папки проекта (остановите прежний процесс бота через Ctrl+C):

```powershell
docker compose up -d --wait
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py run_moderation_bot
```

Миграция `0027_disputedecision_disputedelivery` добавляет журнал решений и доставок, не изменяя балансы.
Токен и список администраторов остаются прежними. Рабочую БД эта инструкция не очищает.

Ручная проверка на локальной тестовой базе:

Вместо создания рынков через приложение можно создать сразу три готовых спора из PowerShell:

```powershell
.\.venv\Scripts\python.exe manage.py seed_moderation_disputes
```

Команда работает при `DEBUG=True`, создаёт отдельные тестовые аккаунты без Telegram-привязки и три рынка:
«Подтвердить ДА», «Изменить на НЕТ», «Аннулировать». В каждом уже куплены акции на 10 монет,
указан исход ДА, приложен демонстрационный текстовый файл и открыт спор с залогом.
Существующие пользователи и рынки не изменяются. Каждый запуск создаёт новый набор; ничего не удаляет.
После запуска отправьте `/disputes` боту модерации и проверьте каждое из трёх действий.
Основной бот, приложение и web-сервер для принятия решений не нужны; локальный web-сервер нужен только для открытия ссылок на файл/админку.

1. Создайте рынок от одного аккаунта, сделайте покупку от другого. Спор может открыть только участник.
2. Дождитесь конца приёма прогнозов, от автора укажите исход с доказательством.
   Для ускорения на локальном тестовом рынке можно заранее установить прошедшие даты закрытия/результата через Django-админку.
3. В течение окна спора нажмите «Оспорить» от участника и укажите причину. У него спишется залог (обычно 20 монет).
4. В боте модерации отправьте `/start`: придёт уведомление, а рынок появится в «Споры об исходе».
5. Откройте карточку и доказательство. Выберите решение, затем нажмите «Назад»: расчёта быть не должно.
6. Подтвердите решение. Проверьте историю, баланс участника, выплаты и журнал в Django-админке.
7. На отдельных рынках проверьте все три решения. Для ДА/НЕТ проверьте и сохранение, и изменение исхода автора.
8. Вторым администратором откройте тот же спор до первого решения; после решения первого старая кнопка должна сообщить,
   что спор уже рассмотрен. Балансы повторно не меняются. Постороннему аккаунту доступ запрещён.

Автотесты без запуска Telegram и без изменения рабочей базы:

```powershell
.\.venv\Scripts\python.exe -m pytest --ds=config.test_settings -q market/tests/test_disputes_bot.py market/tests/test_moderation_bot.py market/tests/test_moderation_ui.py market/tests/test_moderation_refunds.py market/tests/test_resolution.py
```

Для проверки одновременных решений нужен запущенный PostgreSQL и `--ds=config.postgres_test_settings`.
Локально не запускайте основной бот с тем же токеном одновременно с сервером.

```powershell
.\.venv\Scripts\python.exe -m pytest --ds=config.test_settings -q market/tests/test_moderation_bot.py
```

Ручной сценарий на тестовой БД: жалоба через Mini App → уведомления двум модераторам → подтверждение скрытия → старая кнопка другого модератора не меняет решение → `/history` и восстановление. Проверить отказ постороннему аккаунту и групповому чату. Production-токен для тестов не нужен.
