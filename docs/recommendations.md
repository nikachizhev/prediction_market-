# Персональная лента (без ML)


Обновление rules-v3-text: пояснения убраны из интерфейса. Служебное поле
recommendation_reason сохранено для совместимости API.
По заголовкам доступных рынков считаем локальное лексическое сходство:
слова очищаются от общих вопросительных слов, дат и чисел, сравниваются
четырёхбуквенные фрагменты с IDF и косинусной мерой.
Максимальное сходство с открытыми/купленными за 30 дней вопросами повышает
оценку; максимальное сходство со скрытыми понижает. Скрытый вопрос исключается
из положительных примеров. Отмена скрытия снимает отрицательный сигнал.
Сходство влияет внутри прежних приоритетов и разнообразия категорий,
а также определяет порядок внутри категории до чередования.
Это не семантическая модель: синонимы и смысл отрицаний не распознаются.
Названия не отправляются внешним сервисам. Для небольшой базы расчёт идёт
на запросе по всем отфильтрованным кандидатам до пагинации; при росте числа
рынков нужны предрасчитанные векторы/индекс и ограниченная генерация кандидатов.

Mini App открывает вкладку «Для тебя» (`GET /api/markets?sort=recommended`).
Старые клиенты без параметра сохраняют сортировку hot. Категория и поиск
работают вместе с любым порядком. Ранжирование выполняется в SQL до пагинации.

Приоритеты по порядку:

1. Рынки, где открыт приём прогнозов, кроме собственных.
2. Рынки, в которых пользователь ещё не покупал акции (включая случай, когда
   старую позицию уже полностью продал: факт прежней покупки учитывается).
3. Рынки без перекоса 90/10 и сильнее в любую сторону.
4. Выбранные категории из `Trader.interests`.
5. Чередование категорий внутри одинаковых приоритетов: сначала первый рынок
   каждой категории, затем второй и так далее. Внутри выбранных интересов
   действует тот же принцип; явные интересы остаются выше остальных тем.
6. Поведенческий интерес за 30 дней: один балл за открытый уникальный рынок,
   два за купленный (вместо одного); максимум шесть баллов на категорию.
   Повторы и сумма покупки вес не увеличивают.
7. Число уникальных покупателей за сутки, затем свежесть и ID.

Собственные, закрытые, уже сыгранные и перекошенные рынки опускаются вниз,
но остаются в ленте. Рекомендации используют доступные рынки, не раскрывают
чужие группы, не меняют балансы, котировки или вероятность.
«Горячие», «Новые», «Скоро итог» сохраняют прежний порядок.

## Интересы

Онбординг и блок «Твои интересы» в профиле используют
`PATCH /api/me {"interests": ["games", "weather"]}`.
Пустой массив снимает предпочтения; новых тем это не запрещает.
После сохранения сервер пишет `interests_update` с ключами категорий.
Явные интересы важнее поведенческих. Модель не обучается: веса заданы кодом
в `market/recommendations.py` (версия rules-v2). Старые открытия и покупки
перестают влиять через 30 дней. Скрытие рынка не штрафует всю категорию.

## «Неинтересно»

`POST /api/markets/<id>/dismiss {"dismissed": true}` сохраняет уникальную
пару пользователя и рынка в FeedDismissal. Повторный запрос идемпотентен.
Скрытие действует во всех порядках ленты и в поиске, но не удаляет позицию,
сделки или подписку. Прямая ссылка и раздел «Мои» продолжают работать.

Отмена: тот же endpoint с `false`. В ленте есть кнопка «Отменить» для последнего
скрытия. В профиле «Вернуть скрытые рынки» вызывает
`POST /api/feed/reset-hidden` → `{"restored": число}` только для своего аккаунта.
После скрытия клиент загружает первую страницу заново, чтобы смещение
offset-пагинации не пропустило карточку при последующей загрузке.

## События для будущей модели

- `feed_impression` — карточка видна минимум наполовину; один раз на монтаж
  карточки. Время удержания внимания пока не измеряется.
- `market_open` — переход с карточки ленты на рынок; не каждый способ открытия.
- `market_dismiss`, `market_restore`, `feed_restore_all` — серверные события.
- `interests_update` — сохранение выбранных категорий.

Первые два передаются через `/api/events` и содержат ID доступного рынка
и вид сортировки. Произвольные поля отбрасываются. Клиентские события
считаются сигналами интерфейса, а не доверенным основанием для наград.
Открытия участвуют в сортировке с ограниченным весом. Сервер подавляет
одинаковые события одного пользователя в пределах пяти минут (best effort,
одновременные запросы могут пройти). Показы сами по себе интерес не повышают.

## Где лежат данные и кто их читает

Все данные остаются в PostgreSQL приложения. `market_event` хранит события
с внутренним ID пользователя, `market_trade` — подтверждённые сделки,
`market_feeddismissal` — скрытые рынки, `market_trader.interests` — явные темы.
Сырые события связаны с аккаунтом: это персональные данные, а не анонимный набор.
Рекомендатель читает их на сервере. Внешней нейросети ничего не отправляется.

Миграция 0024 создаёт агрегированную витрину
`analytics.recommendation_daily`: московский день, название события,
количество событий и уникальных пользователей. Без ID, текстов и props.
Подключите её к существующему Metabase, графики: показы, открытия, скрытия,
изменения интересов и число пользователей по дням. После миграции повторите
`python manage.py setup_metabase_role`, если роль уже была настроена.
Существующая `analytics.events` даёт BI более подробный доступ к событиям
с внутренними ID: доступ к Metabase должен быть только у команды.

Без Metabase: `python manage.py recommendation_report --days 30` выводит JSON
со сводкой за последние 30 суток, без идентификаторов пользователей.
Отчёт не создаёт файлы и не выгружает данные во внешние сервисы.

Счётчики открытий/показов — диагностика активности, не точный CTR и не
доказательство эффективности: пока нет ID выдачи, позиции, эксперимента и
атрибуции сделки к показу. Для следующего этапа нужны серверные ID выдач,
фиксированные группы A/B и метрики участия/возврата вместе со скрытиями.
Вводить ML стоит после накопления этих данных и сравнения с rules-v2.

Окно ранжирования 30 дней не удаляет события. Политика срока хранения,
плановая очистка и сброс поведенческой истории пользователем пока не реализованы.
При росте данных следует заменить запросы истории предрасчитанным профилем
категорий; сейчас индекс `(trader, name, created_at)` ускоряет выборку событий.

## Запуск и проверки

Примените миграции 0023 и 0024 командой `manage.py migrate`,
пересоберите Mini App и перезапустите приложение. Проверки включают порядок
по интересам, демоцию рынков, приватность, скрытие/отмену, пагинацию и контракт
клиента. В базовой карточке остаются отдельные запросы истории/статистики;
их пакетная загрузка не входит в этот этап.
