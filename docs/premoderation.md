# Проверка перед публикацией

Ветка `market-premoderation`. Это техническая премодерация по правилам продукта,
не юридическое заключение и не гарантия отсутствия запрещённого содержания.

## Рынки закрытых чатов и вызовы (фаза 3e)

Рынок закрытого чата и вызов 1 на 1 (спека E3, E11) открыты сразу, проверка идёт в фоне теми же правилами.
Рынок чата: `publication_state="approved"` сразу, состояние проверки — `background_check`
(pending → checking → clear / review / error / rejected). Отказ отменяет рынок через `services.annul`
с возвратом и сообщениями; сомнение, ошибка и три сбоя подряд оставляют рынок открытым и зовут модератора
(очередь бота и админка — те же). Правка текста запускает проверку заново и рынок не скрывает.
Вызов: `Challenge.check_state`, решения — действиями в админке.
Миграция 0039 открывает рынки чатов, зависшие в очереди, без сообщений создателям.
Всё остальное ниже относится к рынкам общей ленты.

## Что меняется

Новый Question (Mini App, старый сайт, GitHub/A/B-источник, админка) начинается
с publication_state=pending. До approved он не доступен через публичные страницы,
API, поиск, похожие рынки, чатовые подборки, анонсы или торговлю. Автор видит
свои непроверенные вопросы в «Мои», отдельный endpoint `/api/publication-drafts`.
Постмодерация/жалобы/споры остаются независимыми и не отключаются.

Статусы: pending → checking → approved / review / rejected / error.
review — ручная очередь; error повторяется не чаще раза в 5 минут, после трёх
попыток запросов уходит в ручную очередь. Нет ключа, HTTP-ошибка, таймаут,
неверный JSON или остановленный воркер не приводят к публикации.
Потерянная задача после падения процесса подхватывается по истечении 5-минутной аренды.

Автоматическое approved возможно только для разрешённых тем software, study,
games, sports, community, без признаков чувствительных персон/персональных данных
и с самооценкой модели >=0.95. Это эвристика, не откалиброванная вероятность.
Неизвестные темы, сомнения, внешние ссылки вне серверного списка — review.
Явное нарушение при уверенном reject — rejected. Политика, насилие, незаконные
действия, здоровье/смерть конкретных людей и чужая частная жизнь запрещены
в промпте продукта. Автоматической проверки содержания сайтов нет: ссылки
не скачиваются; ссылку из разрешённого домена нельзя считать гарантией безопасности.

Модели передаются название, правила, варианты, источник и сроки всех подрынков.
Не передаются Telegram ID, профиль или история чата. Пользовательский JSON
отделён от системного промпта как недоверенные данные. Ответ строго проверяется;
лишние поля, нечисловая уверенность, NaN и неизвестные решения запрещены.
Текст >20000 символов направляется человеку без API-запроса.
LLM всё равно может ошибаться; нужны выборочные проверки и работающие жалобы.

## Деньги и изменения

Существующее списание субсидии при создании остаётся резервом. Пока вопрос
проверяется, торговать нельзя. При rejected стандартный services.annul атомарно
возвращает субсидию; повторный отказ не начисляет деньги заново. Все варианты
одобряются/отклоняются вместе, дочерние вопросы не проходят отдельное голосование.
Очередь не меняет дату дедлайна: просроченный вопрос не публикуется автоматически.

Изменение заголовка, правил, вариантов, источника или сроков через Model.save
сбрасывает одобрение всей семьи. Результат старой версии не применяется:
контролируются SHA-256 содержимого и UUID аренды; HTTP выполняется без DB-блокировок.
Для изменения подрынка и применения решения используется блокировка корня.
Прямые SQL, QuerySet.update и bulk_create — доверенные внутренние операции,
они обходят Model.save. Не используйте их для пользовательского редактирования
контента; при добавлении новых импортёров это обязательное условие ревью.

PublicationDecision сохраняет версию текста, решение, фиксированную причину,
модель, исполнителя и время; админка не позволяет редактировать/удалять журнал.
Модератору требуется активный staff-аккаунт с market.change_question.
В отдельном модерационном боте доступна кнопка «Публикация рынков» и команда
`/publications`: очередь корневых рынков в review/error, полный текст со всеми
вариантами, одобрение или отклонение с подтверждением. Доступ — только приватный
чат Telegram ID из MODERATION_ADMIN_IDS. Решение привязано к версии содержимого;
старые кнопки после изменения текста или другого решения не действуют.
Уведомления сохраняются отдельно для каждого администратора, повторяются при
ошибке Telegram и подхватывают уже существующие решения review/error. Pending и
checking сначала обрабатывает автоматический воркер. Отклонение использует общий
сервис отмены с возвратом резерва, одобрение публикует весь рынок с вариантами.

В списке Question фильтр publication_state и действия «Одобрить публикацию…» /
«Отклонить публикацию…». Одобрение не отменяет отдельное модераторское скрытие.
Действие сначала показывает подтверждение со всеми текстами. Подписанный токен
содержит ID, хеш, решение и модератора, действует час; изменённая после просмотра
версия не публикуется старым подтверждением.
После отклонения автор создаёт исправленный вопрос заново; уже опубликованные
нарушения рассматриваются существующей постмодерацией.

## Запуск

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py run_premoderation
# Один проход для диагностики:
.\.venv\Scripts\python.exe manage.py run_premoderation --once
```

PREMODERATION_ENABLED=1 по умолчанию, независимо от ASSIST_ENABLED и настроек чата.
PREMODERATION_API_KEY / PREMODERATION_URL / PREMODERATION_MODEL по умолчанию
используют LLM_API_KEY / LLM_BASE_URL / LLM_MODEL. Нужен JSON chat-completions API.
Без ключа остаётся ручное одобрение; создания публикаций без проверки не будет.
Не выключайте PREMODERATION_ENABLED на публичном сервере для обхода очереди.
В тестовых settings флаг выключен явно, а новые тесты включают его с моками API.

Миграция 0031 добавляет поля/журнал и сохраняет уже существующие рынки как approved:
старые тексты не считаются заново проверенными, их нужно отдельно аудировать.
Слияние не должно автоматически отменять рынки или менять старые балансы.
Локальная/удалённая рабочая БД в этой задаче не мигрировалась автоматически.
Проверки SQLite используют моки классификатора. Проверка на PostgreSQL в этой
сессии недоступна: локальная база не ответила на подключение.

В deploy/systemd добавлен pm-premoderation; update.sh после миграций устанавливает
и запускает службу, setup-server.sh включает её при первой установке.
PR #25 мониторинга не слит и в эти изменения не включён. Позже можно добавить
метрики очереди, времени ожидания, ошибок модели и доли ручных решений.
