# CLAUDE.md — внутренний рынок прогнозов (MVP)

## Что за проект

Внутренний рынок прогнозов для крупной компании (целевой заказчик — Т-Банк). Сотрудники ставят игровую валюту на исходы событий внутри компании, компания получает агрегированную вероятность.

Главная идея: **рынок ведёт себя сам.** Вопросы создаются и разрешаются автоматически из рабочих систем (трекер задач, платформа A/B-тестов). Корпоративные рынки обычно умирают, потому что их некому вести и в них мало участников; мы закрываем обе проблемы: автоматизацией вопросов и маркет-мейкером вместо книги заявок.

Сейчас цель одна — **работающее MVP для завтрашней презентации** с надёжным сквозным демо-сценарием (см. ниже). Всё, что не нужно для демо, не делаем.

## Стек

- Python 3.12, Django 5, SQLite.
- Фронт: серверные шаблоны Django + минимальный vanilla JS. Chart.js через CDN для графиков. Никакого SPA и сборщиков.
- HTTP к GitHub: `requests`. Конфиг: `python-dotenv` (`.env`).
- Тесты: `pytest` + `pytest-django`.
- Больше зависимостей не добавлять без явной необходимости. Статистику (z-тест, нормальная CDF) пишем сами через `math.erf`, без scipy/numpy.

## Структура

```
config/        настройки, корневые urls
market/        ядро: модели рынка, lmsr.py, services.py, views, шаблоны
sources/       адаптеры источников вопросов: base.py, github.py, abtest.py, sync.py
abmock/        заглушка внешней платформы A/B-тестов (свои модели и страницы)
```

`abmock` имитирует **внешнюю систему**. Приложение `market` не импортирует `abmock` напрямую, только через адаптер `sources/abtest.py`. Это граница, по которой потом подключается реальная платформа экспериментов.

## Архитектурные правила

- **Все изменения денег и состояния рынка — только через `market/services.py`**: `quote`, `buy`, `sell` (опционально), `resolve`, `annul`. Вьюхи и шаблоны тонкие, бизнес-логики в них нет.
- Каждая сделка и каждое разрешение — в `transaction.atomic()` с `select_for_update()` на вопрос и пользователя. Иначе гонки при одновременных ставках.
- Балансы и суммы — `Decimal`, квантуем до 0.01. Математика LMSR — во `float`, результат конвертируем в `Decimal`. **Стоимость сделки округляем вверх** (в пользу организатора), иначе можно «печатать» деньги на округлении.
- Код, идентификаторы, комментарии — на английском. Весь текст интерфейса — на русском.
- Type hints везде, где не мешает Django.

## Модели (ядро)

- `Trader` — участник (без авторизации, выбор из списка, текущий хранится в сессии): `name`, `pseudonym`, `show_real_name`, `github_login` (nullable), `balance` (стартовый 1000).
- `Question` — рынок: `title`, `resolution_criteria` (текст однозначного критерия), `source_type` (`manual` / `github` / `abtest`), `source_ref` (уникален вместе с `source_type` — идемпотентность синхронизации), `deadline`, `status` (`open` / `closed` / `resolved` / `annulled`), `outcome` (`yes` / `no` / null), `b`, `q_yes`, `q_no`, `initial_prob`, `conflicted_traders` (M2M).
- `Position` — `trader`, `question`, `yes_shares`, `no_shares`, `spent`.
- `Trade` — `trader`, `question`, `side`, `shares`, `cost`, `prob_before`, `prob_after`, `created_at`. Источник данных для ленты и графика.
- `Payout` — `trader`, `question`, `amount`, `kind` (`payout` / `refund`).

## Механизм: бинарный LMSR

Маркет-мейкер — контрагент по каждой ставке; книги заявок нет (при десятках участников она была бы пустой).

- Функция стоимости: `C(q) = b · ln(exp(q_yes/b) + exp(q_no/b))`. Считать **только через log-sum-exp**: `m = max(q_yes, q_no); C = m + b·ln(exp((q_yes−m)/b) + exp((q_no−m)/b))`.
- Цена YES: `p = 1 / (1 + exp((q_no − q_yes)/b))`. Цена NO = `1 − p`.
- Стоимость покупки `Δ` акций YES: `C(q_yes+Δ, q_no) − C(q_yes, q_no)`. Для NO симметрично.
- Покупка **на сумму** `m` монет (так вводит пользователь). Замкнутая формула для YES при текущей цене `p`: `Δ = b · (ln(expm1(m/b) + p) − ln(p))`. Для NO — та же формула с `1 − p`.
- Начальная вероятность `p0`: `q_no = 0`, `q_yes = b · ln(p0 / (1 − p0))`.
- Максимальный убыток организатора на рынке: `b · ln(1 / min(p0, 1 − p0))` (при `p0 = 0.5` это `b · ln 2`).
- Параметры по умолчанию: `b = 200`, стартовый баланс 1000, максимальная ставка за сделку 300. Ориентир: при `p = 0.5` ставка 100 сдвигает цену примерно до 0.70.
- Выплата: при YES каждая акция YES стоит 1 монету, акции NO — 0; при NO наоборот. Аннулирование: каждому возвращается его `spent` по вопросу.
- Продажа (опционально): покупка с отрицательным `Δ` той же стороны, не больше, чем есть у пользователя.

Проверки в `buy`: статус `open`, пользователь не в `conflicted_traders`, `0 < amount ≤ min(balance, max_bet)`.

## Источники вопросов

Общий интерфейс в `sources/base.py`:

```python
class QuestionSource(Protocol):
    source_type: str
    def discover(self) -> list[QuestionDraft]: ...          # новые вопросы (title, criteria, source_ref, deadline, initial_prob, conflicted_logins)
    def check(self, question: Question) -> SourceUpdate | None: ...  # CLOSE_BETTING / RESOLVE_YES / RESOLVE_NO / ANNUL
```

`sources/sync.py: sync_all()` — для каждого источника вызывает `discover` (создаёт недостающие вопросы по `source_ref`) и `check` для незавершённых вопросов, применяет обновления через `market/services.py`. Вызывается кнопкой «Обновить» в интерфейсе и командой `sync_sources`. Ошибка одного источника (сеть, лимит API) не должна ронять остальные и интерфейс — логируем и показываем сообщение.

### GitHub (`sources/github.py`)

- Подключение: пользователь вводит ссылку на репозиторий → модель `GitHubRepo(owner, name)`. Токен берётся из `GITHUB_TOKEN`.
- У issues в GitHub **нет дедлайна**, он есть только у вех (`milestone.due_on`). Поэтому:
  - по каждой вехе с `due_on` → «Будет ли веха «{title}» закрыта до {дата}?»;
  - по каждой issue с меткой `predict`, привязанной к вехе с `due_on` → «Будет ли задача #{n} «{title}» закрыта до {дата}?». Без метки вопросы не создаём, чтобы не заваливать рынок.
- API: `GET /repos/{o}/{r}/milestones?state=all`, `GET /repos/{o}/{r}/issues?labels=predict&state=all` (отфильтровать элементы с ключом `pull_request` — это PR).
- `source_ref`: `gh:{owner}/{repo}:milestone:{number}` / `gh:{owner}/{repo}:issue:{number}`.
- Дедлайн: дата из `due_on`, конец этого дня по `Europe/Moscow` (`TIME_ZONE = "Europe/Moscow"`).
- Разрешение:
  - закрыта с `state_reason = "completed"` и `closed_at ≤ deadline` → YES сразу, не дожидаясь дедлайна;
  - закрыта с `state_reason = "not_planned"` → аннулирование;
  - дедлайн прошёл, открыта → NO;
  - веха: `state = closed` и `closed_at ≤ due` → YES; просрочена и открыта → NO.
  - Разрешение окончательное: повторное открытие issue его не отменяет.
- Конфликт интересов: логины `assignees` → `Trader.github_login` → `conflicted_traders`.
- Опционально (способ 2): ручное создание вопроса по ссылке на issue/PR/веху с условием из фиксированного списка («закрыта до даты», «PR смёржен до даты», «в вехе закрыто ≥ X% задач к дате»). Свободный текст условий не поддерживаем — его нельзя разрешить автоматически.

### A/B-тесты — заглушка (`abmock/` + `sources/abtest.py`)

- Модель `Experiment`: `name`, `hypothesis`, `metric`, `author` (Trader), `status` (`draft` / `running` / `finished` / `cancelled`), `baseline_rate` (например 0.04), `true_lift` (скрытый, для симуляции), `n_per_group`, результаты: `n_a`, `x_a`, `n_b`, `x_b`, `z`, `p_value`.
- Страницы заглушки «Платформа экспериментов»: создать, запустить, завершить, отменить.
- Вопрос создаётся для эксперимента в статусе `draft`: «Даст ли вариант B статистически значимый рост «{metric}»?». `initial_prob = AB_BASE_RATE` (в settings, 0.25 — большинство тестов не выигрывают). Автор эксперимента → `conflicted_traders`.
- Критерий (писать в `resolution_criteria`): YES, если односторонний z-тест для разности долей даёт `p < 0.05` в пользу B. Отмена теста → аннулирование.
- `running` → CLOSE_BETTING (ставки закрываются в момент старта, чтобы никто не ставил, подсмотрев промежуточные результаты).
- `finished` → симуляция: `x_a ~ Binomial(n, baseline_rate)`, `x_b ~ Binomial(n, baseline_rate · (1 + true_lift))` (`random.binomialvariate`, Python 3.12). Z-тест: `p̂ = (x_a+x_b)/(n_a+n_b)`, `se = sqrt(p̂(1−p̂)(1/n_a + 1/n_b))`, `z = (x_b/n_b − x_a/n_a)/se`, `p_value = 1 − Φ(z)`, `Φ(z) = 0.5·(1 + erf(z/√2))`. Результат показывать на странице эксперимента.
- `cancelled` → ANNUL.
- Для предсказуемого демо: `true_lift` задаётся при создании (например 0.3 почти гарантирует значимость при `n_per_group = 20000`).

## Интерфейс (страницы)

- `/` — список вопросов: вероятность, источник, дедлайн, статус; кнопка «Обновить источники».
- `/q/<id>/` — страница вопроса: крупная вероятность, график вероятности во времени, анонимная лента сделок («кто-то купил YES на 50, 55% → 62%»), объём и число участников, критерий разрешения. Своя позиция и потенциальная выплата. Форма ставки с превью (JSON `GET /q/<id>/quote?side=yes&amount=100` → новые акции, новая цена, выплата при выигрыше).
- `/leaderboard/` — топ-10 по прибыли + строка текущего пользователя. Прибыль = баланс + позиции по текущей цене − стартовый капитал. Имя или псевдоним — по настройке пользователя.
- `/me/` — баланс, позиции, переключатель «показывать имя / псевдоним», поле логина GitHub.
- `/switch-user/` — выбор текущего пользователя.
- `/sources/github/` — подключение репозитория.
- `/abmock/` — платформа экспериментов (заглушка).
- `/admin/` — ручное создание и разрешение вопросов (страховка).

**Приватность:** кто как поставил, видит только сам участник. Всем остальным видно только состояние рынка целиком (цена, график, анонимная лента, объём, число участников).

## Демо-сценарий (приоритет №1 — он должен работать всегда)

1. Заглушка A/B: создаём эксперимент «Новый онбординг карты» → на рынке появился вопрос с вероятностью 25%.
2. Два пользователя ставят в разные стороны, цена и график двигаются.
3. «Запустить тест» → ставки закрыты. «Завершить» → симуляция, z-тест, рынок разрешён, выплаты, лидерборд обновился.
4. GitHub: в демо-репозитории создаём issue с меткой `predict` в вехе с дедлайном → «Обновить» → вопрос появился → ставка → закрываем issue в GitHub → «Обновить» → разрешено YES.

A/B идёт первым: он полностью под нашим контролем. GitHub зависит от сети.

`seed_demo --reset` создаёт: 5–6 пользователей (Аня, Борис, Вика, Гоша, Даша, ...), 2–3 эксперимента в разных статусах, один ручной вопрос, историю сделок за последние несколько дней (чтобы графики и лидерборд не были пустыми).

## Порядок работы

1. Модели, `lmsr.py`, `services.py` + тесты.
2. `abmock` + адаптер + страница вопроса → первая сквозная цепочка.
3. Лидерборд, `/me/`, `seed_demo`.
4. GitHub-источник.
5. Опционально: продажа позиции, создание вопроса по ссылке, бейджи «Против толпы» и «Первый голос» (считаются на лету).

## Тесты (обязательный минимум)

- LMSR: цены YES+NO = 1; стоимость по замкнутой формуле совпадает с разностью `C`; купить и продать то же количество — стоимость 0; начальная цена равна `p0`; убыток организатора не превышает оценки; нет переполнения при больших `q`.
- Сервисы: баланс не уходит в минус; конфликтный пользователь не может ставить; нельзя ставить в `closed`/`resolved`; сумма выплат = число выигравших акций; аннулирование возвращает `spent`.
- Z-тест на известных значениях.
- Правила разрешения GitHub на замоканных ответах API. **Тесты не ходят в сеть.**

## Вне объёма MVP (не делать)

Авторизация и SSO, книга заявок, бот в мессенджере, реальная интеграция с Jira/платформой A/B, сезоны лидерборда, калибровка, категории, фильтр комплаенса, уведомления, вебхуки, Celery, SPA/TypeScript-фронт. Всё это — «следующие шаги» в презентации.
