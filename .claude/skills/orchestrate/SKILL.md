# Оркестрация задачи по спеке

Задача пользователя: $ARGUMENTS

## 1. Понять объём

- Прочитай нужные разделы `docs/spec.md` (только их), `docs/tasks.md`, раздел `docs/api.md`, относящиеся макеты `docs/mockups/*.dc.html`.
- Посмотри текущий код по теме: что уже есть, что сломается.
- Если спека и код расходятся — скажи пользователю, не переписывай молча (правило из CLAUDE.md).

## 2. Решить: сам или агенты

Агентов запускай, только если:
1. есть независимые потоки работы, которые можно делать параллельно;
2. и объём настолько большой, что параллельность реально экономит время.

Делай сам, если задача цельная, шаги зависят друг от друга или хватит прямого подхода. Не раздавай мелочи: каждый агент заново читает контекст проекта — это дорого.

## 3. Если раздаёшь — сначала общая основа

Параллельные ветки конфликтуют в `market/models.py`, миграциях, `config/settings.py`, `requirements.txt` и контракте API. Поэтому до запуска агентов сделай сам ветку `miniapp-<эпик>-base` от `miniapp`:
- все новые модели и поля + **одна** миграция;
- новые параметры в `config/settings.py`;
- новые зависимости в `requirements.txt` (с обоснованием);
- контракт API (типы и эндпоинты) в `docs/api.md` — по нему фронтенд работает параллельно с бэкендом;
- строки задач в `docs/tasks.md` (таблица ID / эпик / цель / файлы / зависит / статус) и принятые решения.
Прогони тесты, закоммить, слей в `miniapp` (`git merge --no-ff`).

## 4. Брифы агентам

Агенты — `isolation: "worktree"`, в фоне. Каждый бриф самодостаточен:
- **Ветка:** «создай ветку `miniapp-<эпик>-<коротко>` от ветки `miniapp`» — явно от `miniapp`: worktree может стартовать не с той ветки.
- **Python:** `/home/kirillsultan/study/2course/PI/prediction_market/.venv/bin/python` (venv лежит в основной папке, в worktree его нет). Для фронтенда — симлинк `miniapp/node_modules` из основной папки, не коммитить.
- Что прочитать (конкретные разделы спеки, контракт, макеты) и что сделать — по пунктам, с принятыми решениями.
- Какие файлы трогать и **какие не трогать** (чужие зоны других агентов).
- Тесты: что покрыть; команда `<python> -m pytest --ds=config.test_settings -q`, всё зелёное.
- Коммиты на своей ветке, коротко по-английски, без `Co-Authored-By`; не сливать, не пушить.
- Формат отчёта: что сделано, файлы, тесты, результат, сомнения — без пересказа кода.

## 5. Проверка и слияние

Не верь отчётам на слово:
- `git merge-base --is-ancestor miniapp <ветка>` — ветка от правильной базы;
- в worktree агента прогони тесты сам;
- сливай по одной (`git merge --no-ff <ветка> -m "Merge <ветка>"`), конфликты в `market/api/views.py` / `urls.py` обычно — «оставить обе стороны»;
- после всех слияний: `manage.py check`, `makemigrations --check --dry-run`, тесты на SQLite и `--ds=config.postgres_test_settings`, в `miniapp/`: `npm run typecheck`, `npx vitest run`, `npm run build`;
- сверь стыки между ветками (фронтенд вызывает ровно те эндпоинты и поля, что сделал бэкенд);
- если есть UI — открой экраны в браузере на временной SQLite-базе в scratchpad (не трогая локальный PostgreSQL), с `make_init_data`.
